# Написать issue

Инструмент — MCP `user-GitKraken`, `issues_create` и `issues_get_detail`. Перед первым вызовом — `GetDynamicTools`. `gh` и curl к GitHub не вызывать. Организация `firstBitSportivnaya`, репозиторий `1c-programmer-profiles`, provider `github`.

## Тело

Как у формы `.github/ISSUE_TEMPLATE/change.yml`:

- Область: одна или несколько из content, ui, db, domain, deploy.
- Кто сталкивается — не заполнять, если роль ни при чём, например для deploy.
- Что сейчас.
- Что должно быть.
- Критерии приёмки: 2–5 пунктов «Дано / Когда / Тогда». Хотя бы один негативный (ошибка или отказ).
- Для реализации: файлы и что не менять. Это не поле формы, но без него следующий агент собирает контекст заново.

Для экранов каждый критерий потом станет тестом в `e2e/`. Для deploy и документации в теле прямо написать, чем проверять (команда или ручной сценарий) и что e2e нет.

## Перед созданием

1. Критерий можно проверить. Два прочтения — сначала вопрос человеку, не issue.
2. Негативный критерий есть.
3. Область выбрана.
4. Дубля нет: `issues_get_detail` по номерам, которые уже звучали в разговоре, и по заголовку, если человек дал ссылку. Совпадает смысл — не создавать второй.

Очередь из плана — отдельные issue по зависимости, не один issue на весь план. Код и CI не смешивать с правкой только правил, если план их развёл.

## После ошибки создания

`issues_create` и `pull_request_create` иногда отвечают ошибкой, хотя объект уже есть. Список `issues_assigned_to_me` неполный, по нему дубль не искать.

1. Перед вызовом запомнить наибольший номер, который уже встречался. Нумерация issue и pull request общая.
2. После ошибки — `issues_get_detail` по номерам выше него по очереди, пока не найдётся объект с тем же заголовком или не вернётся «не найдено». Для pull request сверить ещё ветку через `pull_request_get_detail`.
3. Нашли — не повторять. Не нашли — один повтор.
